# Library-wide rules (`[library]`, mainly `[requirements]`)

What the standard says once, in Clause 20, for **every** library facility: how the library text is to be read, what a program may and may not do with library names, and what freedom a conforming implementation has. Overview: [[cpp17-lib-introduction]]. Named template-argument requirements (CopyConstructible, Hash, ...) are on [[library-named-requirements]]; the allocator requirements are on [[allocators]].

## How to read the library clauses (`[description]`, `[definitions]`)

- Function semantics use fixed elements, in this order when present: **Requires** (preconditions), **Effects**, **Synchronization**, **Postconditions**, **Returns**, **Throws**, **Complexity**, **Remarks**, **Error conditions** (`[structure.specifications]/3`). A violated Requires element is undefined behavior unless the Throws element says an exception is thrown for that case (`[res.on.required]/1`).
- "Equivalent to <code>" means the code is a specification, not necessarily the implementation. The Requires/Throws/Postconditions/Complexity of the function itself supersede those of the equivalent code (`[structure.specifications]/4`).
- Complexity bounds are **upper bounds**; a better implementation still conforms, and a "negative" operation count means zero (`[structure.specifications]/6-7`).
- Requirements are stated on **expressions**, not on member functions: "++x is valid", not "operator++ is a member" (`[structure.requirements]/3`). `char_traits` plays that role for strings and iostreams (`/2`).
- Library classes are described by *behavior*; representation, extra private members, and the existence of implicitly-generated special members are unspecified (`[objects.within.classes]`, `[functions.within.classes]`). The label EXPLICIT in the text means "conditionally explicit" ([[cpp17-classes]]). Declarations marked "exposition only" are not part of the interface.
- **Bitmask types** (e.g. `ios_base::fmtflags`, `launch`, `regex_constants::syntax_option_type`): implementable as an enum with overloaded operators, an integer, or a `bitset`; elements are distinct non-zero values with pairwise-disjoint bits; "set" is `X |= Y`, "clear" is `X &= ~Y` (`[bitmask.types]`). **Enumerated types** may be a real enum or a synonym for one (`[enumerated.types]`).
- Defined terms worth knowing (`[definitions]`): *valid but unspecified state* (invariants hold, operations behave per spec); *referenceable type* (object type, function type without cv/ref-qualifier, or reference); *replacement function* (non-reserved function whose definition the program supplies) vs. *handler function*; *required behavior* (what any definition must do) vs. *default behavior* (what the library's own definition does); *stable algorithm*; *traits class*; *NTCTS*.

## Organization and headers (`[organization]`, `[using]`)

- Everything lives in `std` (or nested namespaces) except `operator new`/`operator delete`; whether a name is in the namespace itself or an inline namespace inside it is unspecified (`[contents]/2`). A bare library name in the text means `::std::name` (`/3`).
- 61 C++ headers (Table 16) plus 26 `<cname>` wrappers for C headers (Table 17, including `ccomplex`, `ctgmath`, `cstdalign`, `cstdbool`, `ciso646`, `cuchar`). `<cname>` has the content of `name.h` but inside `std`; whether the names also appear in the global namespace is unspecified. The `name.h` spellings and four deprecated `<cname>` headers are in Annex D ([[cpp17-annex-d-compatibility-features]], `[depr.c.headers]`). C macros stay macros, C functions stay functions, and C++ keywords are never macros in these headers (`[headers]/4-7`).
- Annex K (the `_s` functions) names may appear in the global namespace (never in `std`) when any header is included (`[headers]/9`).
- A **freestanding** implementation needs only an implementation-defined header set including at least `<ciso646>`, `<cstddef>`, `<cfloat>`, `<limits>`, `<climits>`, `<cstdint>`, `<cstdlib>` (with `abort`, `atexit`, `at_quick_exit`, `exit`, `quick_exit`), `<new>`, `<typeinfo>`, `<exception>`, `<initializer_list>`, `<cstdarg>`, `<type_traits>`, `<atomic>` (`[compliance]`).
- Headers may be included in any order and repeatedly (except `<cassert>`, whose effect tracks the current `NDEBUG` each time); a header must be included outside any declaration and before first use, no diagnostic required (`[using.headers]`). Library entities have external linkage, default `extern "C++"`; the language linkage of C library names is implementation-defined (`[using.linkage]`). See [[linkage]].

## What a program may not do (`[constraints]`)

All of these are **undefined behavior** unless noted:

- Add declarations or definitions to `std` (or nested namespaces), `posix`, or any top-level `stdN` namespace (digits after `std`). The one carve-out: a program may add a specialization of a standard template to `std` if it depends on a user-defined type, meets the original template's requirements, and is not otherwise forbidden (`[namespace.std]/1`).
- Explicitly specialize a *member* function, member function template, or member class template of a library class (template), or declare a deduction guide for a library class template (`[namespace.std]/2`). Explicit instantiation of a library template needs a declaration depending on a user-defined type and requirement-conforming (`/2`). Declaring `std` inline is ill-formed without diagnostic (`/3`).
- `#define`/`#undef` a name declared in any standard header, a keyword, an identifier with special meaning, or an attribute token while a standard header is included (`[macro.names]`).
- Declare a name reserved to the implementation: library object names with external linkage (also in the global namespace), global function signatures from headers, C-library names with `extern "C"` linkage, `::T`/`std::T` for each C library type `T` (`[extern.names]`, `[extern.types]`). Literal-suffix identifiers without a leading underscore are reserved for the standard (`[usrlit.suffix]`).
- "Zombie names" in `std` stay reserved even though removed: `auto_ptr`, `unary_function`, `binary_function`, `bind1st`/`bind2nd`, `ptr_fun`, `mem_fun*`, `random_shuffle`, `unexpected`, `set_unexpected`, `get_unexpected`, `unexpected_handler`, ... (`[zombie.names]`).
- Supply a file whose name matches a standard header's derived file name in a standard include place (`[alt.headers]`).
- Pass an invalid argument value (out-of-domain, bad pointer); pass an array argument whose pointer does not support all the required accesses; an rvalue-reference parameter may be assumed to be the only reference to its argument (`[res.on.arguments]`).
- Access a library object outside its lifetime, or make library calls from several threads that cause a data race (`[res.on.objects]`).
- Install replacement or handler functions that violate their *required behavior*; throw from a replacement function, handler, or destructor unless allowed; instantiate a template with types whose operations violate the Requirements subclauses; use an incomplete type as a template argument unless that component says it is allowed (`[res.on.functions]`).

**Replacement functions**: a program may define the global allocation and deallocation functions (the `operator new`/`delete` families of `<new>`); the replacement takes effect before program start, must not be `inline` (no diagnostic required) (`[replacement.functions]`). See [[dynamic-memory-support]] and [[new-and-delete-expressions]].

**Handler functions**: `set_new_handler` and `set_terminate` (and the `get_` counterparts) are data-race-free; a call to a `set_` function synchronizes with later calls to the same `set_` and the matching `get_` (`[handler.functions]/4`). See [[exception-support]].

Derived classes: virtual member functions of library base classes may be overridden by the program (`[derived.classes]`).

## What implementations may and must do (`[conforming]`)

- **Headers**: a header may include other headers and must provide everything in its synopsis (and in the synopses of headers it is shown as including); shared entities must be defined so that any order of inclusion works (`[res.on.headers]`).
- **Signatures**: calls to non-member functions must behave as if no extra overloads exist; no additional default arguments; whether any library function is `inline` is unspecified; member functions may have a different overload set as long as calls that select a documented overload behave identically (`[global.functions]`, `[member.functions]`). Library-internal calls to non-operator non-member functions do **not** use ADL unless specified (`[global.functions]/4`).
- **constexpr**: only functions the standard says are `constexpr` may be declared so (`[constexpr.functions]`).
- **Stable** algorithms: sorts keep the relative order of equivalent elements; remove/copy algorithms keep the order of retained elements; merges put first-range elements before equivalent second-range ones (`[algorithm.stable]`).
- **Reentrancy** is implementation-defined unless specified (`[reentrancy]`).
- **Data races** (`[res.on.data.races]`): a library function may not access or modify objects visible to other threads except through its own arguments (non-const arguments for modification, including `this`), nor access objects reachable through container elements except by calling functions the spec requires. Iterator operations from container/string members may read but not modify the container. Internal shared state is allowed if hidden and protected; observable work is done in the calling thread unless specified. (The note that hidden `static` buffers would violate this is informative.) See [[memory-model-and-data-races]].
- **Derivation**: classes may derive from implementation-reserved bases; virtual stays virtual and non-virtual stays non-virtual; distinct names mean distinct types; library types are non-final unless stated (`[derivation]`). Friendship between library classes is unspecified (`[protection.within.classes]`).
- **Exceptions** (`[res.on.exception.handling]`): library functions fail only with exception types from their Throws element (or derived); C library functions do not throw (except via program-supplied callbacks); **library destructors never throw**; functions without a Throws element but with a potentially-throwing specification may throw implementation-defined exceptions, ideally derived from the standard exception classes ([[exception-support]], [[standard-exception-classes]]); an implementation may add `noexcept` to a non-virtual function.
- Traceable pointer location for user pointers stored by the library (`[res.on.pointer.storage]`); `error_code` from the OS uses `system_category()` ([[error-codes-and-system-error]], `[value.error.codes]`).
- **Moved-from library objects** are in a *valid but unspecified* state unless stated (`[lib.types.movedfrom]`).

## Differences from the C standard library (Annex C.5, `[diff.library]`)

Annex C.5 (informative) summarizes where the C++ library's versions of C library material differ from the C standard. It is mostly a pointer list: the detail lives in the clauses it cites. Language-side differences from C are on [[cpp-vs-c-differences]]; the rule that behavior and preconditions stay those of C unless stated is `[library.c]` ([[cpp17-lib-introduction]]).

- **Headers** (`[diff.mods.to.headers]`): the C headers of `[depr.c.headers]` are provided but their use is deprecated ([[cpp17-annex-d-compatibility-features]]). There are no C++ headers for the C headers `<stdatomic.h>`, `<stdnoreturn.h>` and `<threads.h>`, and those C headers are not part of C++ either. `<ccomplex>` and `<ctgmath>`, and the C headers `<complex.h>` and `<tgmath.h>`, carry none of the C content; they merely include other C++ library headers. `<ciso646>`, `<cstdalign>` and `<cstdbool>` are meaningless in C++; use of `<ccomplex>`, `<cstdalign>`, `<cstdbool>` and `<ctgmath>` is deprecated.
- **Names that are keywords or types in C++** (`[diff.mods.to.definitions]`): `char16_t`, `char32_t` and `wchar_t` are distinct types and keywords, not typedefs, and the C headers' definitions of them are absent (`<cuchar>`; `<cstddef>`, `<cstdlib>`, `<cwchar>`). `static_assert` (instead of a macro in `<cassert>`), the alternative operator tokens (`and`, `or`, `not`, `xor`, `bitand`, `bitor`, `compl`, `and_eq`, `or_eq`, `xor_eq`, `not_eq`, no longer macros of `<ciso646>`), `alignas` (`<cstdalign>`) and `bool`/`true`/`false` (`<cstdbool>`) are keywords, not macros. `NULL` (in `<clocale>`, `<cstddef>`, `<cstdio>`, `<cstdlib>`, `<cstring>`, `<ctime>`, `<cwchar>`) is an implementation-defined C++ null pointer constant (`[support.types]`). Compare the C-versus-C++ keyword entries on [[cpp-vs-c-differences]].
- **Declarations** (`[diff.mods.to.declarations]`): in `<cstring>` the functions `strchr`, `strpbrk`, `strrchr`, `strstr` and `memchr`, and in `<cwchar>` `wcschr`, `wcspbrk`, `wcsrchr`, `wcsstr` and `wmemchr`, have different signatures; the synopses (`[cstring.syn]`, `[cwchar.syn]`) declare a const-pointer overload and a non-const overload for each, and notes there say the behavior is as in C. `<cwchar>` declares no `wchar_t` type (`[cwchar.syn]/1`). `<cstddef>` additionally declares `nullptr_t`.
- **Behavior** (`[diff.mods.to.behavior]`): `atexit`, `exit` and `abort` of `<cstdlib>` behave differently, and `longjmp` of `<csetjmp>`. Annex C.5 only names them. In the text it points to, `[support.start.term]` has `abort` and `_Exit` end the program without running destructors of automatic, thread or static objects or the `atexit` functions; `exit` destroys the calling thread's thread-storage objects, then static-storage objects and runs the `atexit` functions (order in `[basic.start.term]`), never destroys automatic objects, calls `std::terminate` if a registered function lets an exception escape, then flushes and closes C streams (see [[program-startup-and-termination]], [[cpp17-lib-language-support]]). `[csetjmp.syn]/2` makes a `setjmp`/`longjmp` pair undefined when the same jump written with `catch`/`throw` would run any non-trivial destructor of an automatic object.
- **`offsetof`** (`[diff.offsetof]`, `[support.types.layout]/1`): accepts a restricted set of types. Applying it to a class that is not standard-layout is conditionally-supported, it is never type-dependent (value-dependent only if the type is dependent), the result for a static data member or a function member is undefined, and it is `noexcept` and throws nothing.
- **Allocation functions** (`[diff.malloc]`, `[c.malloc]`): `aligned_alloc`, `calloc`, `malloc` and `realloc` are restricted. They keep the C semantics but do not obtain storage by calling `::operator new`, and `free` does not call `::operator delete`. Storage from them counts as implicitly declared reachable (the pointer-safety facility on [[allocators]]) from allocation until deallocation; a note recommends treating it as if allocated with `operator new` ([[dynamic-memory-support]]).
